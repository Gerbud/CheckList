## 1. Созданные модели

1. `Store` — магазин с уникальным коротким кодом, часовым поясом и признаком
   активности.
2. `EmployeeProfile` — профиль стандартного Django User, связанный с магазином
   и ролью `employee`, `manager` или `administrator`.
3. `ChecklistTemplate` — активируемый шаблон чек-листа конкретного магазина.
4. `ChecklistTemplateVersion` — версия шаблона со статусами `draft`,
   `published`, `archived` и автором создания.
5. `ChecklistSection` — упорядоченный раздел версии шаблона.
6. `ChecklistItem` — упорядоченный пункт раздела с настройками комментария при
   невыполнении и статуса «не применимо».
7. `DailyChecklist` — ежедневный чек-лист сотрудника с жизненным циклом
   `draft`, `completed`, `reopened`.
8. `DailyChecklistItem` — неизменяемый исторический снимок пункта шаблона.
9. `ChecklistAnswer` — ответ на снимок пункта со статусом, комментарием,
   автором и временем ответа.
10. `AuditLog` — журнал значимых бизнес-операций со старыми и новыми значениями,
    инициатором и метаданными запроса.

Основные связи:

```text
Django User ──1:1── EmployeeProfile ──N:1── Store

Store ──1:N── ChecklistTemplate
                └──1:N── ChecklistTemplateVersion
                            └──1:N── ChecklistSection
                                        └──1:N── ChecklistItem

Store + EmployeeProfile + ChecklistTemplateVersion
                └── DailyChecklist
                      └──1:N── DailyChecklistItem
                                  ├──N:0..1── ChecklistItem (source_item)
                                  └──1:1── ChecklistAnswer

AuditLog ──N:1── Store
         └──N:0..1── Django User
```

## 2. Реализованные бизнес-правила

- Номер версии уникален внутри одного шаблона.
- Для одного шаблона допускается только одна опубликованная версия.
- Опубликованные версии, их разделы и пункты защищены от обычного изменения и
  удаления; изменение содержимого выполняется новой версией.
- Публикация архивирует предыдущую опубликованную версию атомарно.
- Один сотрудник может иметь только один чек-лист на дату в одном магазине.
- Ежедневный чек-лист создаётся только из актуальной опубликованной версии.
- Активные пункты шаблона копируются в `DailyChecklistItem`; одновременно для
  них создаются ответы `pending`.
- Исторический снимок не меняется при выпуске новой версии шаблона и защищён от
  сохранения или удаления обычными model-методами.
- Для ответа `failed` обязателен непустой комментарий.
- `not_applicable` запрещён, если снимок пункта его не разрешает.
- `pending` не допускается у завершённого чек-листа.
- Ответы завершённого чек-листа заблокированы до повторного открытия.
- Сотрудник может редактировать и завершать собственный чек-лист.
- Менеджер и администратор своего магазина могут работать с чек-листами
  сотрудников и повторно открывать завершённые чек-листы.
- Обычный сотрудник не может повторно открыть завершённый чек-лист.
- Все изменяющие сервисные операции выполняются в `transaction.atomic`; в
  местах возможной гонки используются `select_for_update` и ограничения БД.
- Явно журналируются создание чек-листа, изменение статуса и комментария
  ответа, завершение, повторное открытие и публикация версии.
- `AuditLog` и исторические снимки доступны в Django admin только для чтения.
- Команда `seed_checklist` идемпотентно создаёт магазин «5 Планет», шаблон,
  опубликованную версию №1, 3 раздела и 18 пунктов.

## 7. Проблемы и ограничения

1. SQLite игнорирует `select_for_update`; полноценные проверки конкурентных
   блокировок необходимо выполнять на PostgreSQL. Уникальные ограничения БД
   всё равно защищают ключевые инварианты локально.
2. Сервис создания чек-листа ожидает ровно одну опубликованную версию среди
   всех активных шаблонов магазина. Если магазину потребуются разные типы
   ежедневных чек-листов, в API нужно добавить явный выбор шаблона.
3. Аудит и часть проверок гарантируются сервисным слоем. Прямой
   `QuerySet.update()`, bulk-операция или SQL способны обойти model-level
   защиту; прикладной код должен использовать `checklists.services`.
4. Seed-публикация выполняется системно без пользователя, поэтому `created_by`
   версии и `actor` аудита допускают `NULL`.
5. Согласно явному правилу комментарий обязателен для любого `failed`, даже
   если поле `comment_required_on_failure` в будущем будет равно `False`.
   Назначение этого флага стоит уточнить перед созданием интерфейса.
6. Стандартный Django admin не поддерживает вложенные inline без сторонних
   пакетов: разделы редактируются inline у версии, пункты — inline у раздела.
7. Интеграционные тесты на PostgreSQL и тесты реальной конкурентности пока не
   добавлены.
8. Два первых коммита имеют одинаковое сообщение `Initialize Django project`,
   поэтому история менее информативна, чем могла бы быть.
