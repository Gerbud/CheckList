# Гарантийный отдел

## Реализовано

- отдельное Django-приложение `warranty`;
- доступ к веб-разделу только для системного администратора;
- идемпотентный импорт обращений, истории и файлов из Bitrix;
- хранение полного исходного снимка каждой записи для аудита и повторной обработки;
- поиск, фильтр по статусу, карточка клиента и изделия;
- ответственный, приоритет, срок решения, комментарий;
- история изменений, вложения, работы, диагностика и запчасти;
- модель Telegram-обсуждения и локальная история сообщений;
- архивирование обсуждения при закрытии и восстановление при повторном открытии.

## Почему Telegram-тема, а не отдельная удаляемая группа

Telegram Bot API не даёт надёжного сценария «удалить группу, а потом восстановить её вместе с перепиской». Удаление темы также уничтожает сообщения. Поэтому целевая схема — закрытая супергруппа гарантийного отдела в режиме форума и отдельная тема на каждое обращение:

1. новое обращение создаёт тему;
2. бот публикует карточку и закрепляет её;
3. входящие сообщения и файлы зеркалируются в БД;
4. закрытие обращения вызывает `closeForumTopic`;
5. повторное открытие вызывает `reopenForumTopic`, история остаётся на месте.

## Результаты анализа рынка

В модель заложены общие возможности профильных систем:

- Odoo Repairs: связка обращения и ремонтного заказа, серийный номер, гарантийный признак, ответственный, запчасти, резервирование, ремонтные этапы, возврат клиенту и платный ремонт;
- Zoho Desk: приоритеты, каналы поступления, категории, SLA, сроки, эскалации, вложения и статусы ожидания;
- сервисные helpdesk/repair-системы: единая временная шкала, назначение исполнителей, диагностика, смета, складские позиции, документы и уведомления.

## Импорт

Экспортёр `warranty/bitrix_readonly_export.php` выполняет только `SELECT`. Импорт запускается командой:

```bash
python manage.py import_bitrix_warranty export.json --files-root /path/to/files
```

Повторный запуск безопасен: обращения сопоставляются по `(source, external_id)`, история и файлы — по внешним ID.

## Двусторонняя связь с «1С-Битрикс: Управление сайтом»

Устанавливаемый модуль находится в `bitrix-module/pinel.warrantysync`. Он работает с существующими таблицами `warranty` и `warranty_log`, перед запуском проверяет обязательные поля и разрешает менять только `UF_STATUS` и `UF_COMMENT`.

Модуль `pinel.warrantysync` установлен и включён на сервере Pinel 20.08.2026 в `/local/modules/pinel.warrantysync`. Архив сохранён рядом как `/local/modules/pinel.warrantysync.zip`. Общий HMAC-секрет настроен в параметрах Bitrix и локальном игнорируемом `.env`. Подписанная связь проверена из Django операциями `health` и `claims.list`; модуль версии 1.0.0 ответил успешно.

### Установка в Bitrix

1. Скопировать каталог `bitrix-module/pinel.warrantysync` целиком в `/local/modules/pinel.warrantysync` на старом сайте.
2. В административной панели открыть **Настройки → Настройки продукта → Модули** и установить «Pinel: обмен гарантийными обращениями».
3. Открыть **Настройки → Настройки продукта → Настройки модулей → Pinel: обмен гарантийными обращениями**.
4. Сгенерировать общий секрет не короче 32 символов, сохранить его и включить API.
5. Проверить, что `https://СТАРЫЙ-САЙТ/warranty-sync/` доступен новому серверу по HTTPS.

На Django-сайте добавить в `.env`:

```dotenv
BITRIX_WARRANTY_SYNC_URL=https://СТАРЫЙ-САЙТ/warranty-sync/
BITRIX_WARRANTY_SYNC_SECRET=тот-же-длинный-секрет
BITRIX_WARRANTY_SYNC_TIMEOUT=20
```

После обновления кода выполнить:

```bash
python manage.py migrate
python manage.py sync_bitrix_warranty
```

Для постоянного обмена запускать команду каждую минуту через cron с блокировкой от параллельного запуска. Изменения Bitrix загружаются по курсорам новых обращений и журнала, изменения статуса и комментария на Django-сайте помещаются в надёжную исходящую очередь.

Начиная с версии модуля `1.3.0`, основной путь входящих изменений — подписанный webhook. В настройках модуля включите отправку и укажите:

```text
https://checklist.es-helper.ru/warranty/bitrix/webhook/
```

Модуль подписывает тело тем же HMAC-секретом, который используется для API. Он отправляет уведомления после создания и изменения обращения и после загрузки файла. Django по уведомлению сначала забирает данные из Bitrix, затем сразу создаёт, обновляет, закрывает или восстанавливает Telegram-тему. Минутный cron следует сохранить как резерв на случай временной недоступности одного из серверов. На Beget обе гарантийные команды запускаются единым файлом `run_beget_cron.sh` вместе с остальными периодическими задачами проекта.

Имя автора изменения берётся из имени и фамилии пользователя Bitrix. Если они не заполнены, модуль передаёт мобильный, личный или рабочий телефон; телефонный логин используется последним телефонным fallback. Если телефона тоже нет, отображается ID пользователя Bitrix.

Индекс ссылок на чертежи Greenworks обновлять раз в сутки:

```bash
python manage.py refresh_greenworks_drawings
```

Команда читает публичный каталог Greenworks и сохраняет ссылки локально. Поэтому создание и обновление Telegram-тем не зависят от скорости внешнего сайта.

Запросы подписываются HMAC-SHA256 общим секретом и действуют пять минут. Секрет не передаётся в URL или теле запроса.
